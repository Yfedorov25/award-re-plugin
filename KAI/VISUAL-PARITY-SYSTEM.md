# VISUAL-PARITY-SYSTEM — трек побудови «кожна візуальна помилка рівно 1 раз»

> Створено сесія 11 (2026-07-08). Причина: пари hero/меню/funnel стояли «✅ 1-в-1 закрито», а при піксельній звірці з живим виявилось багато грубих розбіжностей (дзеркальний хедер, регістр UPPERCASE↔Title, задвоєна R, різні розміри контейнерів). Корінь (доведено 3 аудитами по коду + PAI-доктрині): **у системі нуль піксельних порівнянь із живим**; статус «готово» дозволено на технічному GREEN (drift/docHeight/0-errors/лічильники), сліпому до візуалу. Пара відео §4 BUILD-PROTOCOL існує, але НІЧИМ не примушена.
>
> **ЦЕЙ ФАЙЛ = single source of truth побудови гейтів. Не забути = добудувати всі 7 пунктів. Порядок за силою-до-вартості. Кристалізація = закон Miessler «capture a learning → crystallize into a rule so we don't do that anymore».**

## 🎥 G20 `site-scan` — СКАНЕР САЙТУ В ДИНАМІЦІ (запит Єгора сесія 11: «щоб я не знімав відео сам»)
> Мета Єгора дослівно: «щоб ти чи софт міг взяти новий сайт і повністю сам зняти відео, пройти по всіх секціях і на телефоні і на десктопі, і не тільки код а ще дизайн-елементи як очима просканувати саме в ДИНАМІЦІ не тільки в статиці, і далі повторювати». Це знімає з Єгора ручне знімання відео.
>
> **ЧЕСНИЙ РОЗПОДІЛ ПРАЦІ (закон цього гейта):** скрипт = РУКИ+ЛІНІЙКА (проходить сайт, знімає відео+кадри desktop&mobile, рахує покадровий diff, будує борд). Агент = ОЧІ+СУД (дивиться на зняті кадри й судить «динаміка збігається / це slop / дисбаланс»). НЕ вбудовувати «оцінку дизайну» в скрипт як поріг — це брехливий поріг. Піксель+рух міряє скрипт; «гарно/правильно» вирішує агент, дивлячись.

**Що робить G20 (специфікація):**
- Вхід: `--live <url>` + `--ours <url>` (або профіль `<site>.parity.json` зі списком сторінок і тригерів).
- Проходить КОЖНУ секцію: авто-скрол кроком (напр. 0.5 екрана) + кліки по заданих тригерах (меню-бургер, дріл-плита, таби, каруселі — з профілю).
- Знімає на КОЖНОМУ кроці: кадр PNG + пише відео (playwright `recordVideo`), у ДВОХ в'юпортах desktop 1440×820 + mobile 390×844.
- Той самий маршрут на живому і нашому → покадровий diff (переюз canvas-diff з G15) → % на кожен крок руху (не лише фінальний стан).
- Борд `site-scan-board.html`: рядок на крок [ЖИВЕ-кадр | НАШ-кадр | diff] + число + посилання на обидва відео. Агент гортає й судить динаміку.
- Профіль робить це переносним «від сайту до сайту» — Єгор заповнює конфіг раз на сайт (URL живого/наш/сторінки/тригери/маски динаміки), увесь набір гейтів працює.

**Статус G20:** 🟢 СИНХРОН КРОКІВ ДОЗРІВ (сесія 12). Файл `scripts/site-scan.mjs`. Профіль `scripts/parity-profiles/aircenter.parity.json`. Прогін home desktop: **11 кроків обидві сторони, 0 misaligned** (число валідне).
**Уроки/фікси сесії 11 (у код вписані):**
- Locomotive/Lenis НЕ реагує на `window.scrollBy` → драйв через `page.mouse.wheel` + `page.mouse.move` у центр (wheel б'є під курсор).
- **Людський скрол (правило Єгора, виміряно з Desktop-air.mp4)**: крок = БАГАТО дрібних тіків (tick_px 80, tick_ms 16, ~350px/с), НЕ один стрибок. І людськи у відео, і докручує Lenis. Константи в профілі.
- Маски: `iframe`/vimeo на home = full-screen → з'їдали ВЕСЬ кадр → diff 0%. Прибрано з home (чесний шум спіралі краще за фальшивий 0%).

**✅ СИНХРОН КРОКІВ ВИПРАВЛЕНО (сесія 12) — розсинхрон 60/32 усунено в корені:**
- **Корінь (доведено кодом):** кроки матчились по ІНДЕКСУ кадру, а крок = фіксовані px. Живий довший (піни) → 60 кадрів, наш → 32 → step-N показував РІЗНУ глибину → фальшиві 57%.
- **Фікс: спільна СІТКА ПРОГРЕСУ.** Обидві сторони йдуть до однакових цілей нормалізованого прогресу прокрутки `[0.0, 0.1, …, 1.0]` (profile `progress_step`), знімають кадр на кожній цілі. step-N живе і step-N наше = ТОЙ САМИЙ % глибини за побудовою.
- **Універсальний вимір прогресу в сторінці (`READ_PROGRESS`, справжня функція):** native/Lenis `scrollY/(scrollHeight-innerH)`, АБО (коли Locomotive тримає scrollY=0) — з `translateY` повзунка кастомного скролбару `/(trackH-thumbH)`. **Знахідка сесії 12:** на aircenter (Locomotive) ЄДИНИЙ рухомий сигнал прогресу = `.c-scrollbar_thumb` transform; window.scrollY/lenis/loco усі стоять на 0. Доведено пробою: живий (thumb) і наш (native) обидва досягають 0.1/0.2/…/1.0 з точністю **±1%**.
- **Прогін home desktop (доказ):** 11/11 кроків, depth L/O збігаються ±0.017 на кожному кроці (0.10/0.11, 0.50/0.51, 1.00/1.00), **0 misaligned**. Борд показує depth-мітку L/O на кожен крок + прапор misaligned (Δprogress>0.03 → крок виключається з aligned-avg).
- **ЧЕСНЕ ЧИСЛО тепер = 63% avg (max 84%), НЕ «1-в-1».** Це вже НЕ артефакт вимірювання — це РЕАЛЬНА розбіжність структури: на depth 0.50 живий у секції Location (будівля+хвилини 1/3/7/11), наш — у Format (спіраль «intelligent harmony»). Наш сайт коротший/менше пінів → на однаковому % глибини різні секції. Плюс дзеркальний хедер видно на кадрах (наш AIR+Menu / живий бургер+♡+CHOOSE OFFICE). Тобто **валідне число САМЕ Є діагнозом** — воно каже «структура сторінки розійшлась», що й треба було довести інструментом замість «на око».

**✅ СЕКЦІЙНЕ ВИРІВНЮВАННЯ ПО ЯКОРЯХ ДОДАНО (сесія 12, запит Єгора):** новий режим `align: "sections"` у профілі. Замість рівномірної сітки 10% — цілі скролу = **прогрес кожної секції-якоря** (`READ_ANCHORS`: `[data-scroll-section]`→fallback`section`, targetProgress = docTop/(scrollH−innerH)). Матч по `section_map: [[liveIdx,oursIdx],…]` (порожня = авто-парування пропорційно індексу). Тоді step-N = **ТА САМА секція** навіть при різній довжині/кількості секцій. Перевикористовує весь progress-драйвер (доведено: докрутка до targetProgress якоря #4 живого = 0.376 vs ціль 0.377). Вирішує головну проблему «наш коротший → різні секції на однаковому %» + діагностика структури (борд показує L#↔O# на кожен крок). У section-mode прапор misaligned вимкнено (сторони НАВМИСНЕ на різних %, матч по секції). Живий home = 11 секцій-якорів, наш = 7 → авто-парування 11 кроків. ⚠️ `section_map` ПОКИ порожня (авто) — після перегляду борда вписати семантичну відповідність (hero↔hero, location↔location, footer↔footer).
**Два режими доповнюють один одного (знахідка сесії 12):** desktop живий рухається ТІЛЬКИ від `mouse.wheel` (scrollIntoView Locomotive ігнорує); mobile живий НЕ рухається ні від wheel ні від CDP-touch (scrollH застигає на 844, overflow:hidden) — але **секційні targetProgress досяжні тим самим thumb-драйвером**. Тож `align: "sections"` — це і є шлях до mobile-diff.
**⏳ mobile grid (390×844)** — прогнано: **10/11 кроків misaligned** (жива сторона застрягла на depth 0.00 — Locomotive-mobile слухає touch, не wheel; scrollH=innerH=844). **Прапор misaligned спрацював ПРАВИЛЬНО** — чесно виключив брехливі кроки замість фальшивого 65%. Це доказ що захист працює. Mobile-diff іде через `align: "sections"` (наступний прогін).

**МЕЖА (чесно):** скрипт НЕ «розуміє дизайн» сам. Він доставляє агенту повний матеріал (рух desktop+mobile обох сайтів + числа), щоб агент судив очима замість Єгора. Це і є вся ідея — Єгор більше не знімає відео, агент знімає й дивиться.
