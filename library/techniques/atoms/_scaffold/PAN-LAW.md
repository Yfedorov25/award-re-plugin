# ПАНОРАМА (горизонтальний закон) — переносний рецепт, S54

Виведено на `amenities-parking`, вердикт Єгора на борді S54. Застосовний до БУДЬ-ЯКОГО атома,
де камера в медіа рухається по горизонталі: проїзд залою, обліт, тревелінг уздовж фасаду.

## 1. ЧИМ МІРЯТИ (і чим НЕ міряти)

⛔ **НЕ інтегралом зсуву** (`cumX`, «на скільки % ширини поїхав вміст»). У сцені з рухом камери
горизонтальний потік НЕ однорідний: `dx(x) = a + b·(x − W/2)`, де `b` це розширення (в кадр
заходить більше сцени), `a` це чиста бічна складова. Один глобальний зсув їх ЗЛИВАЄ. На parking
цей інтеграл ранжував відкинуту оком збірку ВИЩЕ за прийняту.

✅ **Позиція вікна екрана в КООРДИНАТАХ СЦЕНИ.** Одиниця це ширина стартового кадру, на старті
вікно = [0, 1]. По кожній парі кадрів беремо потік НА КРАЯХ (саме він каже, що входить у кадр
і що виходить) і переносимо межі екрана в сцену:

| величина | що означає |
|---|---|
| `sL` | де стоїть ЛІВИЙ край екрана в сцені |
| `sR` | де стоїть ПРАВИЙ край екрана (куди «доїхали») |
| `G = sR − sL` | у скільки разів ШИРШЕ сцени влазить у кадр («зала відкривається») |

Дві збірки з однаковим `sR` можуть бути фізично різні: одна доїхала ВІДКРИТТЯМ (G ×1.5), друга
ПОВЗАННЯМ убік (G ×0.95). Око читає саме цю різницю.

🔴 **Нормалізація це частина величини.** `G` рахується відносно ВЛАСНОГО старту збірки. Збірка з
тіснішим стартом дасть більший `G` при тій самій абсолютній ширині фіналу. Подавати `G` без
стартової ширини вікна ЗАБОРОНЕНО: Єгор зловив саме таку подачу на борді S54.

## 2. ІНСТРУМЕНТ

```
node scripts/pan-parity.mjs --control              # контроль на ВІДОМІЙ відповіді, 3/3
node scripts/pan-parity.mjs --atom <id>            # наш рендер проти live
node scripts/pan-parity.mjs --atom <id> --seq <dir> # прогнати чужу секвенцію (для храповика)
```

Модуль: `scripts/lib/panparity.mjs`. Дві умови гейта: розбіжність `G` ≤ 15% і хід правого краю
`sR ≥ sR_live − 0.25`. `sR` НЕ гейтимо зверху (див. нормалізацію), зверху судить око.

**Обовʼязково оголосити фазу** в `self-check.config.json`:
```json
"pan": { "ourRange": [0, 0.349], "liveFrames": [1, 92], "states": 44 }
```
Поза фазою руху камери горизонтального закону немає і вимір там = шум. Перша версія гейта міряла
весь ролик і занизила live з ×1.51 до ×1.35.

## 3. ЯК ПОБУДУВАТИ ПАНОРАМУ З КЛІПУ

Кліп 3:4 у портретний вʼюпорт 585×1266 не влазить по ширині, тому панорама береться з
**розкладу вікна кропу**, а не з самого кліпу.

1. Зняти власний хід кліпу: `sceneWalk` по повних кадрах. Якщо `G_кліпу ≈ 1.0`, кліп зали не
   відкриває, і все відкриття доведеться дати вікном.
2. Стеля вікна: `wMax = floor(висота_кліпу · 585/1266)`. Для 1244×1664 це **768px з 1244**.
3. Стартове вікно: `w0 = wMax / G_ціль`. Для G ×1.51 це ≈ 504px.
4. Розклад на кожен кадр: ширина з кривої `G(page)` live, позиція `x` з того, куди має доїхати
   правий край. Кадр кліпу на кожній позиції сторінки береться з ЗАКОНУ ХОДУ КАМЕРИ (S), розклад
   вікна його НЕ міняє.
5. Перевірити гейтом і показати оку на борді.

**Три робочі форми, які варто памʼятати:**
- вікно сталої ширини, лише їде (G ≈ 1.0) = бічне повзання, око це відкидає;
- вікно ширшає, стоїть на місці = зала відкривається, але правий край не доїжджає;
- вікно ширшає І їде = обидві ознаки разом (обрано Єгором на parking).

## 4. ХРАПОВИК

До гейта обовʼязково прикласти **негативний еталон**: збірку БЕЗ панорами (вікно сталої ширини,
нульовий хід). Вона мусить FAIL-ити. На parking храповик: C ✅ · B ✅ · A(0.66) ❌ · 0.19 ❌ ·
0.00 ❌, де 0.66 і 0.19 це збірки з відомою відповіддю ока.

## 5. ЧОМУ ЦЕ ВЗАГАЛІ ТРЕБА БУЛО ПИСАТИ

Закон панорами двічі губився (S52 і S53), бо жив ЛИШЕ в реалізації: у `transform-origin` і в
коментарі коду. У CLAIMS-словнику горизонтальних вердиктів не було взагалі, у SPEC не було
жодного рядка про горизонталь. Тому мінімум для будь-якого атома з панорамою:
рядок `PAN:opens` / `PAN:slides` / `PAN:none` у CLAIMS-таблиці CHOREO **плюс** інваріант у SPEC
**плюс** `pan` у конфігу. Три місця, інакше при наступній заміні механізму закон зникне знову.

# INTERACTION-СМУГА ХАРНЕСА (S54, рішення Єгора)

Не про панораму, але лежить поруч, бо це друга діра ПОКРИТТЯ, знайдена тієї ж сесії.

**Проблема.** Харнес судить лише scroll-атоми з чистою `render(p)`. Атоми, де закон драйвиться
ТАПОМ, під це не підпадають: у `terraces` немає `render` взагалі, а в `forest` він є, але це ШИМ
`p<0.34?0:(p<0.67?1:2)`. Ретрофіт scroll-гейтів на них дав би ХИБНЕ ЗЕЛЕНЕ (судився б шим).

**Смуга `scripts/interaction-check.mjs`** судить три речі, усі про закон:
1. `reachability` — стан досяжний оголошеною дією, без console-error;
2. `state-diff` — стан РЕАЛЬНО відрізняється від дефолту і від ІНШИХ станів (інакше мертвий тап
   або стан-двійник пройшли б);
3. `return` — дія-закриття повертає рівно в дефолт (для hotspot це toggle, для cycle це стрілка назад).

**Оголошення в `self-check.config.json`:**
```json
"interaction": { "resetSel": ".lead", "settleMs": 700, "band": [0.10, 0.92],
  "stateDiffMin": 0.03, "returnDiffMax": 0.015,
  "states": [ { "id": "aperture", "sel": "[data-marker=\"aperture\"]", "closeSel": ".lead" } ] }
```

**КАЛІБРАЦІЯ на ВІДОМИХ відповідях (обовʼязкова, зроблена S54):** у копію атома вкидався баг,
смуга мусила його зловити ТИМ САМИМ виміром, який за нього відповідає.
- вкинуто «мертвий тап» (знято обробник) → `state-diff` 0.0% при порозі 3% ⇒ FAIL ✅ спіймано;
- вкинуто «зламаний toggle» (`closeCard` не закриває) → `return` 33.7% при допуску 1.5% ⇒ FAIL ✅,
  причому перевірки відмінності станів лишились зеленими, тобто виміри не перекриваються.

**ЧОГО СМУГА НЕ РОБИТЬ СВІДОМО:** не порівнює стани з LIVE. У live-відео моменти тапів довільні,
і прив'язка кадрів була б ручною декларацією, тобто підгонкою. Ідентичність станів live↔наш
судить ОКО. Смуга ловить лише СТАРІ КЛАСИ БАГІВ: мертвий тап, стан-двійник, зламаний toggle.

**Результати S54:** terraces 3 стани PASS · forest 2 стани PASS.
